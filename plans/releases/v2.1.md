# v2.1 — Enforce the edge

**Status:** ⬜ not started (v3 roadmap — see [docs/ROADMAP_V3.md](../../docs/ROADMAP_V3.md))
**Depends on:** v2.0 (shipped). **Gates:** v2.2 must not start until **this release's CI is green on a clean machine**.
**Theme:** make the safety rails actually fire, build the CI wall that protects everything after, and fix the latent multi-node convergence-lock bug — the cheapest, highest-trust wins, before anything architecturally risky lands.

**Demo / definition of done (sharp + testable):**
1. Start a room, attach an agent with a policy that **denies** `fs/delete` and scopes `writePaths` to `src/`. Drive a real-ish ACP transcript (mock backend is fine for CI) that tries to (a) delete a file and (b) write `secrets/key.txt`. **Both are blocked: the Y.Doc never mutates, an `AuditEntry` with `action:'policy-deny'` is appended, and the agent sees a rejected tool-call.** A `requireApprovalForDestructive` op surfaces the existing approval gate instead of silently applying. — proven by a new `apps/web/scripts/v2_1-policy-check.mjs`.
2. Every PR runs **GitHub Actions** (`typecheck + lint + build + server vitest + the `apps/web/scripts/*-check.mjs` e2e suite`) against a booted server, and **branch protection blocks merge** unless it's green. A red check cannot land.
3. A **2-node** setup (two server processes sharing one Redis, same room) running concurrent commits **serializes flush+commit** — no interleaved/corrupt commit — proven by `v2_1-lock-check.mjs`; the invariant is documented in `docs/THREAT_MODEL.md` + `docs/SCALING.md` and scale-out stays labeled **experimental**.
4. `docker compose -f docker-compose.yml -f deploy/compose.sandbox.yml up` runs the agent host inside an **OS-level sandbox** (seccomp + read-only bind mounts except the workspace), and an escape attempt (write outside `writePaths`, spawn outside the mount) is denied at the OS layer.
5. `y-codemirror.next` is **vendored, pinned, license-stamped** under `packages/vendor/` and the editor still does remote cursors / origin-tagged remote edits / undo-by-origin — proven by a binding regression test.
6. Basic **rate limiting** is live on auth, agent-spawn, git-push, and the sync handshake; a flood returns `429` (HTTP) / closes the upgrade (WS) without taking the room down.

---

## Goals
- **Make the agent safety rails fire at runtime, not just in unit tests.** Today a configured `AgentPolicy` is enforced by 18 green unit tests in `agent-policy/` but is **never consulted at the live tool-call seam** — `agent/adapter.ts` applies effects with no `enforce()` call, and `agent/acp-backend.ts` emits real fs writes as `requiresApproval:false`. The per-agent policy is **decorative**. This release wires it.
- **Build the CI wall** so nothing below silently re-rots. There is currently **no `.github/workflows/`** at all.
- **Fix the latent multi-node correctness bug** before any "production-ready" messaging: `convergence/lock.ts` is explicitly process-local, yet `docs/SCALING.md §4` claims "with Redis, nothing has to be sticky for correctness." Under scale-out, two replicas hold two independent in-memory mutexes → concurrent `flushAndCommit` on the same bare repo → the corrupt-commit / lost-code failure ADR-000 exists to prevent.
- **Close the agent-RCE gap** with an opt-in OS-level sandbox mapped to the now-enforced `writePaths` (the THREAT_MODEL's "single most important operator control", currently the operator's unaided homework).

## Scope — OUT (deferred / not this release)
- **Real-service verification, real-agent gate, BYO-key `LlmPlanner`, observability/metrics, spend governor** → **v2.2**. v2.1 proves enforcement against the **mock/replayable** path; v2.2 proves it against the real thing. (The transcript-replay harness is v2.2; v2.1's e2e uses the existing mock backend.)
- **Intent-locks / turn-taking, reviewer-agent, blame, agent commit authorship, merge-review surface** → **v2.3** (hard-gated on this CI being green).
- **Live 3-way external-push merge, chaos harness, external audit, GA stamp** → **v3.0**.
- **Per-agent worktree/container isolation** — charter ban (ADR-001). The sandbox is OS-level confinement of the *shared* host, not agent partitioning.
- **Heavyweight rate-limit infra** (distributed quota service, per-user billing tiers) — a small in-process token bucket is the ceiling; the THREAT_MODEL still names the proxy as the operator's primary DoS control.
- **Swapping the CRDT or the editor** — vendoring pins what shipped (ADR-002/003); it does not change engines.

## Build slices (parallelizable via worktrees)

> **Slice 0 lands on the working branch FIRST** so every worktree builds against stable interfaces (exactly the v0.1→v2.0 pattern, [AGENT_HANDOFF.md §2](../../docs/AGENT_HANDOFF.md)). Then A–E fan out into worktrees and integrate back. **Load-bearing slices: A (enforcement) and C (node-lock)** — they carry the correctness/safety weight and get the heaviest tests + review.

### Slice 0 (main) — contracts + scaffold _(blocks all others; tiny, no behavior change)_
**Owns / edits:**
- `apps/server/src/agent/types.ts` — extend `ResolvedHostDeps` and `AgentHostDeps` with an injected **`enforcer`** seam (see interface below). Default `null` = today's behavior, so nothing breaks before Slice A fills it.
- `apps/server/src/convergence/lock.ts` — widen `withRoomLock` to accept an optional injected **`LockBackend`** (the in-memory FIFO mutex becomes the default backend; a Redis lease can be slotted in by Slice C without touching call sites).
- `apps/server/src/convergence/index.ts` — export the `LockBackend` type + a `setLockBackend()` seam.
- `packages/vendor/` — create the directory + a `README.md` describing the vendoring contract (Slice E fills it).
- `pnpm-workspace.yaml` — add `packages/vendor/*` to the workspace globs.

**Exports (the injected interfaces siblings code against):**
```ts
// agent/types.ts — the enforcement seam (Slice A implements, host injects)
export interface ToolCallEnforcer {
  /** roomId+agentId+call → decide before the adapter applies anything. */
  decide(roomId: RoomId, agentId: AgentId, call: PolicyCall): PolicyDecision;
  /** side-effect hook the adapter calls on a deny, so audit lives outside the adapter. */
  onDeny?(roomId: RoomId, agentId: AgentId, call: PolicyCall, decision: PolicyDecision): void;
}
// ResolvedHostDeps gains:  enforcer: ToolCallEnforcer | null;

// convergence/lock.ts — the cross-process lock seam (Slice C implements)
export interface LockBackend {
  withLock<T>(roomId: string, fn: () => Promise<T>): Promise<T>;
}
export function setLockBackend(backend: LockBackend | null): void; // null = in-memory default
```
**Decoupling:** Slice 0 ships *interfaces + null defaults only* — it is behavior-preserving and independently mergeable, so A–E each compile against a frozen contract. Slice A never imports the Redis lease; Slice C never imports the policy engine.

### Slice A (worktree) — **POLICY ENFORCEMENT** at the live tool-call seam _(LOAD-BEARING)_
**Owns / edits:**
- `apps/server/src/agent/adapter.ts` — the single funnel. Call the injected `enforcer.decide(...)` at the top of `recordToolCall` / `recordPending` (and the ACP `write_file` path). On `deny`: do **not** mutate; write a `done:false`/error tool-call snapshot + emit a rejected `tool-call` event; call `enforcer.onDeny`. On `require-approval`: force the call through `recordPending` even if the backend marked it `requiresApproval:false`. On `allow`: today's behavior.
- `apps/server/src/agent/host.ts` — resolve `enforcer` in `resolveDeps()`; thread it into the adapter (it already constructs the adapter with `ResolvedHostDeps`).
- `apps/server/src/agent/index.ts` — re-export `ToolCallEnforcer`; let `configureAgentHost` accept it.
- `apps/server/src/v15.ts` — build a `PolicyRegistryEnforcer` that adapts the existing `policies` (`PolicyRegistry`) + `recordAudit` into a `ToolCallEnforcer`. Derive `PolicyCall.destructive` from op kind (`delete` / `run` / force-push) and `PolicyCall.path` from the file op.
- `apps/server/src/index.ts` — pass the enforcer into `configureAgentHost({ terminal, enforcer })`.
- **New:** `apps/server/src/agent/enforce-seam.ts` — the `PolicyRegistryEnforcer` impl + the `op → PolicyCall` mapping (`isDestructive`, `pathOf`), unit-tested.
- **New test:** `apps/server/src/agent/enforcement.test.ts` — deny-doesn't-mutate, require-approval-routes-to-gate, allow-passes, ACP-write-respects-policy, audit-on-deny.
- **New e2e:** `apps/web/scripts/v2_1-policy-check.mjs` (extends the `v0_5-agent-check.mjs` pattern).

**Exports:** `PolicyRegistryEnforcer` (from `enforce-seam.ts`); the adapter now consults enforcement before every mutation.
**Decouples via:** the `ToolCallEnforcer` interface from Slice 0 — the adapter depends on the *interface*, never on `agent-policy/` or `audit/` directly. `enforcer=null` ⇒ legacy behavior, so the slice is safe to integrate incrementally.
**The fix in one line:** the ACP backend's `writeTextFile` currently emits `requiresApproval:false` (line ~412 of `acp-backend.ts`) — after this slice, a write is still *proposed* but the **adapter** (not the backend) decides whether policy allows/gates/denies it.

### Slice C (worktree) — **NODE-SOUND convergence lock** _(LOAD-BEARING)_
**Owns / edits:**
- `apps/server/src/convergence/lock.ts` — keep the in-memory FIFO mutex as the default `LockBackend`; ensure `withRoomLock` delegates to the injected backend.
- **New:** `apps/server/src/scale/redis-lock.ts` — a `RedisLockBackend` implementing a per-room **lease** (e.g. `SET key val NX PX ttl` + Lua-guarded release, fencing token, bounded wait/retry) over the **same** ioredis client config the scale module already parses (`scale/redis.ts` → `buildRedisConfiguration`). Reuses `redisOptionsFromUrl`; never opens a socket on import (lazy, matching the existing module's discipline).
- `apps/server/src/scale/index.ts` — export `maybeRedisLockBackend(env)` (returns the lease backend when `REDIS_URL` is set, else `null`).
- `apps/server/src/index.ts` — at boot, `setLockBackend(maybeRedisLockBackend() ?? null)` so single-node is unchanged.
- `apps/server/src/scale/status.ts` — surface lock mode in `getScaleStatus()` ("experimental: cross-node lock via Redis lease" vs "single-node in-memory lock").
- **New test:** `apps/server/src/scale/redis-lock.test.ts` — lease acquisition/release, TTL expiry, contention serialization, fencing on a stale holder (uses a mock/in-memory Redis or `ioredis-mock`).
- **New e2e:** `apps/web/scripts/v2_1-lock-check.mjs` — boot **two** server processes sharing one Redis, open the same room on both, fire concurrent `POST /api/rooms/:id/commit` from each, assert a linear commit history (no orphaned/corrupt commit, no lost file).
- **Docs:** `docs/SCALING.md` (fix the false "nothing has to be sticky for correctness" claim in §4; document the lease invariant + the "experimental until v2.2" label) and `docs/THREAT_MODEL.md` (§4.5 / convergence: add the cross-node flush-serialization invariant).

**Exports:** `RedisLockBackend`, `maybeRedisLockBackend`.
**Decouples via:** the `LockBackend` interface from Slice 0 — `convergence/` depends on the interface, not on `scale/`; `scale/redis-lock.ts` reuses only `scale/redis.ts`'s parser. Default null backend ⇒ single-node behavior byte-for-byte unchanged.
**Why load-bearing:** this is the ADR-000 seam under concurrency; getting the lease/fencing wrong reintroduces exactly the corrupt-commit failure v3 exists to make impossible.

## Sequencing + dependencies

**Intra-release order**
1. **Slice 0 (main)** — lands first; freezes the `ToolCallEnforcer` + `LockBackend` interfaces. Nothing else starts until merged.
2. **Slices A, C, D, E** fan out into worktrees **in parallel** (all build against Slice 0's null-default seams).
   - **A and C are the load-bearing pair** — assign the strongest reviewers; their tests are the spine of the release.
   - **B (CI)** can develop in parallel but **integrates last** so it runs the *real* check set (it must reference `v2_1-policy-check.mjs` from A and `v2_1-lock-check.mjs` from C). A no-op skeleton workflow may land early to exercise the pipeline.
3. **Integrate back** to the working branch in order A → C → E → D, then **B turns the wall on** (add the e2e job + apply branch protection).
4. **Coordination point:** A and E both touch `api.ts` (different regions). Land A first; E rebases.

**Cross-release gates**
- **v2.2 must not start** until this release's **CI is green on a clean machine** (`docker compose up` + the e2e suite passes from a fresh clone) — the explicit hard gate in ROADMAP_V3 §"How to build this" and risk #4.
- Scale-out stays **labeled experimental** exiting v2.1; v2.2's 2-node real-Redis tier is what promotes it (and re-runs `v2_1-lock-check.mjs` against real Redis as a release gate). Do not drop the "experimental" label here.
- The sandbox + enforcement land here precisely so the v3.0 external audit has a real agent-runs-code surface to audit (risk #5).

## Test / verification strategy

**Unit (vitest, `pnpm test`)**
- `enforcement.test.ts`: deny → no doc mutation + audit appended; require-approval → routed to `recordPending`/gate; allow → applied; ACP `write_file` respects `writePaths`; `denyTools`/`denyPaths` precedence holds at the seam (re-uses the `agent-policy/policy.test.ts` truth table, now via the live adapter).
- `redis-lock.test.ts`: NX-acquire, TTL expiry, contended serialization, fencing token rejects a stale holder. Use `ioredis-mock` or an injected fake so the unit tier needs no live Redis.
- `ratelimit.test.ts`: refill math, per-class isolation, threshold → 429.
- Existing 18 `agent-policy` + `convergence.test.ts` + `redis.test.ts` must stay green (regression guard).

**e2e (extend the `apps/web/scripts/*-check.mjs` pattern — driven against a booted server)**
- **`v2_1-policy-check.mjs`** (the demo's heart): create room → seed `scratch.tmp` + a `src/` file → attach mock agent with `denyTools:['fs/delete']`, `writePaths:['src']` via `PUT /api/rooms/:id/agents/:id/policy` → prompt it to delete + to write `secrets/key.txt` → assert: file still present, `secrets/key.txt` absent, agent status not stuck, an `AuditEntry{action:'policy-deny'}` is on `getAudit(doc)`, and a `requireApprovalForDestructive` op surfaces `awaiting-approval`. Mirrors `v0_5-agent-check.mjs` mechanics (HocuspocusProvider + field helpers).
- **`v2_1-lock-check.mjs`** (chaos-lite): start two `@ice/server` processes on different ports sharing one Redis (compose `--scale server=2` or two `tsx` boots + a local redis), open the same room via both, fire `Promise.all` of concurrent commits from each node, assert: `GET /commits` shows a single linear history with both commits, no commit references a corrupt tree, no seeded file vanished. This is the v2.1-scale "real-service-ish" test — the minimal Jepsen ancestor the v3.0 chaos harness grows from.

## Risks + mitigations (this release)
1. **Enforcement seam breaks the real-agent flow.** Routing ACP writes through `enforce()` could deadlock the agent (it's blocked on a permission request) if `require-approval` isn't wired back to the ACP `resolveApproval` path. → Reuse the existing dual-dispatch in `host.resolveApproval` (adapter effect **and** `backend.resolveApproval`); enforcement only *chooses* gate-vs-deny-vs-allow, the gate machinery is unchanged. Cover the ACP gate path in `enforcement.test.ts` with a fake backend.
2. **Redis lease incorrectness re-introduces the corrupt-commit bug it's meant to kill.** A naive `SET NX` without fencing lets a stale holder (GC pause > TTL) write after losing the lease. → Use a fencing token + Lua-guarded release; keep the in-memory backend as the single-node default (zero new failure modes when `REDIS_URL` is unset); label scale-out experimental until v2.2 verifies against *real* Redis. Do **not** claim multi-node soundness beyond what `v2_1-lock-check.mjs` proves.
3. **Sandbox is Linux/seccomp-specific and silently a no-op elsewhere.** A self-hoster on Docker Desktop/macOS could believe they're confined when they aren't. → `ICE_AGENT_SANDBOX` is *advisory only* (app logs intent, never asserts confinement); README states the OS caveats plainly; the smoke script is the proof, and it's documented as Linux-host. Confinement is the OS's job, not the app's (THREAT_MODEL trust-boundary stance).
4. **CI flake on the e2e tier (timing-sensitive `sleep`s) erodes the wall's authority.** The existing checks use fixed `sleep`s. → Harden new checks with poll-until-condition helpers (bounded retries) instead of fixed sleeps; make the e2e job retry once on infra-only failure; keep unit tests as the fast, deterministic spine so a flaky e2e never blocks a correct change for long.
5. **Vendoring drifts from upstream and rots (the exact risk #5 we're closing).** → Stamp version+commit in `PROVENANCE.md`, pin exactly, and add a `DEPENDENCIES.md` note on the upgrade/refork procedure so the next council can re-sync deliberately.
6. **Scope creep into v2.2.** Temptation to "just verify against a real agent now." → Out by charter: v2.1 proves enforcement against the **mock**; the real-agent gate is v2.2's hard, separate gate. Hold the line.

## Open questions (for the builders)
1. **Lock backend ownership of the bare repo:** is a Redis lease sufficient, or do we also want **room→replica affinity** (sticky room ownership) so a room's flushes always run on one node? Lease is simpler and matches "stateless + Redis"; affinity is more robust but needs the web edge to hash by room. Recommend **lease for v2.1**, note affinity as a v2.2 option. Confirm.
2. **`PolicyCall.destructive` derivation:** which ops are destructive at the seam — `delete`, `run`, force-push, and `write` that *overwrites* an existing file? Or only delete/run? (Affects how often the approval gate fires.) Recommend delete + run + force-push; treat plain `write` as non-destructive (the policy author scopes it via `writePaths`).
3. **Audit on deny — actor:** record the deny under the **agent** actor (it attempted the call) or **system** (the enforcer blocked it)? Recommend `actor:{kind:'agent',id}` with `action:'policy-deny'` + the reason in `detail`, so the run-record (v2.3) reads naturally.
4. **Rate-limit identity in dev-permissive mode:** auth is permissive in dev (no session) — key buckets by client IP when no session exists? Confirm the key strategy so local two-browser demos don't trip limits.
5. **Seccomp profile baseline:** start from the Docker default seccomp profile (deny the dangerous set) and subtract, or hand-author an allow-list? Recommend *default-minus* for breadth/safety, validated by the smoke script. Confirm the egress policy (allow LLM API + git remotes only?).
6. **CI runner for e2e:** does the e2e job need a service-container Redis for `v2_1-lock-check.mjs`, or do we run the 2-node lock check only in a nightly/manual job and keep the per-PR e2e single-node? Recommend: single-node e2e on every PR; the 2-node lock check as a required job with a Redis service container (GitHub Actions supports it cheaply).

## Notes / decisions discovered
- **The decorative-policy bug is concretely in `agent/acp-backend.ts:~412`** (`writeTextFile` emits `requiresApproval:false`) and the absence of any `enforce()` call in `agent/adapter.ts`. Slice A's whole point is moving the decision into the adapter so neither the mock nor the ACP backend can bypass it.
- **`docs/SCALING.md §4 contains a now-false correctness claim** ("with Redis, nothing has to be sticky for correctness") given `convergence/lock.ts` is process-local. Slice C must fix the doc, not just the code.
- The `policies` `PolicyRegistry` and `recordAudit` already exist and are wired into routes — Slice A is *adapting existing parts together at the seam*, not building new engines. Smallest diff, largest risk reduction (ROADMAP_V3 risk #5).
- Promote any real decision discovered here (lease-vs-affinity, destructive-op set) to `docs/DECISIONS.md` as a new ADR and note it in `PROGRESS.md`.
